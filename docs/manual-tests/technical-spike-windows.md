# Windows manual proof — Camera Grid OBS technical spike

Status: **MANUAL PENDING**. Automated tests do not prove real camera transport,
OBS alpha transparency, WebRTC behavior, or absence of captured audio.

Never use a client name, real production room, reused password, or private URL in
screenshots and logs. Generate disposable alphanumeric values for this test.

## Prerequisites

- Windows 10/11, current Chromium browser, and OBS Studio;
- one real webcam (two devices/browsers are preferable);
- two isolated browser profiles or one normal plus one private window;
- Discord may remain the voice path, but mute it during the no-audio check;
- Windows camera permission enabled; microphone permission must not be granted.

## A. Real camera, video-only sender

1. Create disposable values for `STREAM_ID`, `LOBBY_ROOM`, and an alphanumeric
   `TEST_PASSWORD`; do not save them in this repository.
2. Open a guest URL generated by `buildGuestUrl` in a fresh browser profile.
3. Inspect the permission prompt: it may request the camera, but must not request
   the microphone. Deny microphone access if the browser presents it anyway and
   record the browser/version as a failure to investigate.
4. Select the physical webcam and start sharing.
5. In a second isolated profile, open the matching viewer URL generated by
   `buildViewerUrl`.
6. Confirm moving live imagery from the physical camera. A mock, placeholder,
   prerecorded file, or static screenshot is not a pass.

Record: browser versions, camera model, sender/viewer result, and any permission
prompt. Do not record the disposable URLs.

## B. Audio disabled end-to-end

1. With the real camera connected, speak and create obvious nearby sound.
2. Confirm the guest page offers no microphone selector or unmute control.
3. Confirm the viewer produces no audible sound.
4. In OBS, observe the source and master audio meters for at least 20 seconds.
5. Pass only if no audio source is created for the browser feed and no meter
   movement comes from it. `noaudio` in a URL alone is not sufficient proof.

## C. Transparent OBS output

Run only after the local `/output` route exists (Gate B).

1. Add an OBS Browser Source pointing to the local output URL.
2. Set width 1920, height 1080, and leave custom CSS disabled initially.
3. Place a bright color source underneath the Browser Source.
4. Confirm areas outside the camera boxes show the source underneath with true
   transparency, not black or an opaque webpage background.
5. Move and resize a camera in the control panel. Confirm OBS updates without a
   Browser Source reload or a visible WebRTC reconnection.

## D. WebSocket synchronization

Run only after the local panel/output server exists.

1. Open the control panel and output in different browser contexts.
2. Move, resize, hide, and show a camera; confirm the same revision reaches the
   output and the video iframe remains mounted.
3. Stop the local server during a drag, restart it, and confirm the client loads
   a fresh snapshot rather than replaying a stale mutation.

## E. Gate A revocation — lobby/transfer option

Run each check while recording what the **local application** decided separately
from what VDO.Ninja actually allowed. Do not infer one from the other.

1. Join with one disposable invite in Browser A. Approve it explicitly before
   transferring/admitting it to production.
2. Use **Hide**: only the layout box disappears. Publication authorization and
   any separate output-view capability remain unchanged.
3. With Browser A connected, use **Revoke**. Confirm the local invite becomes
   revoked, the box leaves production, and a disconnect request is issued.
   Record separately whether VDO.Ninja actually disconnects the peer.
4. Refresh Browser A and request admission again. The lobby may open, but the
   local application must reject approval for the revoked generation.
5. Paste the same invite into clean Browser B. Repeat the local decision check.
6. Before revocation, use developer tools only on disposable test data to record
   whether the client can observe destination room/password information. After
   revocation, try those previously obtained destination details directly.
   Record the result as a limitation; a successful direct connection must not be
   reworded as an application approval.
7. Disconnect the director. Confirm local approval becomes unavailable. Observe
   whether the guest remains connected and whether another director can claim
   the VDO room. Reconnect the intended director and require explicit approval.
8. Stop and restart the local server. A pending or previously connected browser
   must not become automatically approved. Revoked state must remain revoked.
9. With a different active invite, disconnect and reconnect the guest. The same
   participant and slot must be preserved, but production admission requires a
   fresh explicit approval.

## F. Publication, viewing, and layout controls

1. Block/revoke **publication**: the invite can no longer receive local
   publication approval; output viewing capability is unchanged.
2. Block **viewing**: the output capability can no longer open the protected
   local output; guest publication state is unchanged.
3. **Hide** the camera: only layout visibility changes; neither publication nor
   viewing authorization changes.
4. Any test where one action silently changes another access layer is FAIL.
